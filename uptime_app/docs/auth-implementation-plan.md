# Авторизация с JWT, PostgreSQL и Bun ORM

## Результат и выбор ORM

Реализовать регистрацию по email, подтверждение адреса, вход, выход и восстановление пароля через письмо. Добавить Go API и страницы Next.js. До подтверждения email вход запрещён.

**Выбираем Bun ORM**: для этого проекта подходят модели на Go-структурах, построитель SQL-запросов и интеграция с `database/sql`. Транзакции позволяют атомарно обновлять сессии и одноразовые токены. [Документация Bun](https://bun.uptrace.dev/guide/getting-started.html), [транзакции](https://bun.uptrace.dev/guide/transactions.html).

Использовать:

- `github.com/uptrace/bun` — ORM;
- `github.com/uptrace/bun/dialect/pgdialect` — диалект PostgreSQL;
- `github.com/uptrace/bun/driver/pgdriver` — драйвер;
- `github.com/uptrace/bun/migrate` — версионированные SQL-миграции.

Bun поддерживает SQL-миграции, включая транзакционные файлы `.tx.up.sql`. Версии зависимостей закрепить в `go.mod` и `go.sum` при реализации. [Миграции Bun](https://bun.uptrace.dev/guide/migrations.html).

## Бэкенд и хранение

- Разделить HTTP-обработчики, сервис авторизации, PostgreSQL-репозитории и отправитель писем внутри `backend/internal`. Bun использовать только в слое хранения; HTTP DTO отделить от моделей БД.
- Создать модели пользователей, сессий, истории refresh-токенов, одноразовых токенов и очереди писем. История refresh-токенов нужна для обнаружения повторного использования после ротации.
- Email нормализовать удалением внешних пробелов и приведением к нижнему регистру; уникальность обеспечить ограничением БД. Добавить внешние ключи и индексы для поиска токенов, активных сессий и ожидающих писем.
- Миграции хранить в `backend/migrations`, встроить через `embed`. Добавить отдельную команду с операциями `up`, `status`, `down`; использовать блокировку мигратора. Не изменять схему автоматически при запуске API.
- Настроить пул соединений, проверку подключения при старте и закрытие при завершении. Сохранить таймауты сервера, graceful shutdown и существующий `/api/v1/health`.
- Хешировать пароли через Argon2id с индивидуальной случайной солью. Длина пароля — 12–128 символов, без обязательного состава и обрезания пробелов.
- Access JWT действует 24 часа, содержит `sub`, `sid`, `iss`, `aud`, `iat`, `exp`. Подпись HS256; разрешённый алгоритм фиксирован. JWT-секрет — обязательная переменная окружения, минимум 32 случайных байта.
- Refresh-токен — случайное непрозрачное значение. Абсолютный срок сессии — 30 дней. Хранить только хеши; каждое обновление атомарно заменяет токен. Повторное использование заменённого токена отзывает сессию.
- Middleware проверяет JWT и активность сессии в базе. Выход немедленно отзывает текущую сессию, сброс пароля — все сессии пользователя.
- Подтверждение email действует 24 часа, восстановление пароля — 30 минут. Токены одноразовые, в таблице токенов хранить только хеши; повторная отправка заменяет предыдущий токен того же назначения.
- Ротацию refresh-токена, использование одноразового токена и сброс пароля выполнять через `RunInTx` с блокировками строк. Конкурентный сброс и обновление сессии не должны оставлять действующую сессию после сброса.
- Создание токена и письма объединять в транзакцию. Отправитель использует SMTP, повторяет ошибки с задержкой до пяти попыток. Содержимое очереди, необходимое для отправки ссылок, шифровать отдельным ключом из окружения и удалять после отправки либо окончательного завершения попыток. Секреты не журналировать.

## API и защита

Все маршруты находятся под `/api/v1/auth`.

| Метод и путь | Поведение |
|---|---|
| `POST /register` | `{email, password}`; регистрация и письмо подтверждения |
| `POST /verify-email` | `{token}`; подтверждение адреса |
| `POST /resend-verification` | `{email}`; повторное письмо |
| `POST /login` | `{email, password}`; access JWT и refresh-cookie |
| `POST /refresh` | Ротация refresh-cookie и новый access JWT |
| `POST /logout` | Отзыв текущей сессии и удаление cookie |
| `POST /forgot-password` | `{email}`; письмо восстановления |
| `POST /reset-password` | `{token, password}`; новый пароль и отзыв всех сессий |
| `GET /me` | `{id, email, email_verified}` по Bearer JWT |

- Вход и refresh возвращают `{access_token, token_type: "Bearer", expires_in: 86400, user}`. Ошибки имеют формат `{error: {code, message}}`.
- Регистрация, повторное подтверждение и восстановление возвращают одинаковый `202` для существующих и отсутствующих адресов. Повторная регистрация не меняет пароль существующего пользователя.
- Неверные данные входа — общий `401`; правильный пароль при неподтверждённом адресе — `403` с кодом `email_not_verified`. Невалидные данные и одноразовые токены — `400`, превышение лимитов — `429` с `Retry-After`, недоступность необходимых сервисов — `503`.
- Refresh-cookie: `HttpOnly`, `SameSite=Strict`, без `Domain`, путь `/api/v1/auth`, `Secure` в production. Для cookie-маршрутов проверять `Origin` по настроенному адресу фронтенда.
- Ограничить JSON до 16 КиБ. Ответы авторизации отдавать с `Cache-Control: no-store`.
- Лимиты: 10 попыток входа за 15 минут на сочетание IP/email; 5 запросов регистрации и отправки писем в час отдельно на IP и email; 60 refresh-запросов в минуту на IP.
- Первый выпуск использует лимитер в памяти одного API-процесса. Не доверять произвольным forwarded-заголовкам; для Next.js-прокси явно настроить доверенный источник клиентского IP.
