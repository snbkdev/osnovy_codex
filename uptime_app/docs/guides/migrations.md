# Работа с миграциями PostgreSQL

Гайд для разработчиков и агентов. Структура соответствует [шаблону задачи C/O/S/T](../templates/task.md). Все команды ниже выполняются из `uptime_app/`, если не указано другое.

## C — Контекст: где что лежит

| Путь | Назначение |
| --- | --- |
| `backend/migrations/` | Версионированные SQL-файлы: пары `*.tx.up.sql` и `*.tx.down.sql` |
| `backend/migrations/migrations.go` | Встраивает SQL через `go:embed` и обнаруживает миграции через Bun |
| `backend/cmd/migrate/main.go` | CLI с командами `up`, `status`, `down`; инициализация служебных таблиц, блокировка, таймаут 2 минуты |
| `backend/internal/config/config.go` | `LoadDatabase`: чтение `DATABASE_URL` и настроек пула |
| `backend/internal/storage/` | Репозитории, модели БД и PostgreSQL-интеграционные тесты |
| `backend/internal/storage/auth_integration_test.go` | `testDB` сбрасывает схему тестовой БД; `TestPostgresMigrations` проверяет повторный `up`, статус, блокировку и откат |
| `scripts/backend-env.sh` | Загружает env-файл и запускает команду из `backend/` |
| `Makefile` | `migrate-up`, `migrate-status`, `migrate-down`, `test-integration`, `check`, `build` |
| `compose.yaml` | Локальные PostgreSQL 17 и Mailpit; PostgreSQL доступен на `127.0.0.1:55432` |

API не применяет миграции при запуске. `up` применяет все ожидающие миграции одной группой; `down` откатывает последнюю группу в обратном порядке, а не один файл. На пустой базе первая группа может включать всю схему.

## O — Результат / цель

Изменение схемы воспроизводимо на пустой базе и на базе предыдущей версии с данными. После применения ожидаемые столбцы, индексы, ограничения и данные соответствуют задаче, приложение работает, повторный `up` ничего не меняет. Последствия отката описаны и проверены на отдельной базе.

## S — Границы и порядок работы

### 1. Определить изменение и окружение

Прочитайте [общие инструкции](../../AGENTS.md) и [инструкции backend](../../backend/AGENTS.md). Найдите затронутые SQL, модели и запросы в `backend/internal/storage/`, а также связанные API-контракты.

Зафиксируйте целевую БД (хост, порт, имя без пароля), ожидаемые изменения данных и совместимость с текущей версией API. Для базы с ценными данными заранее подготовьте резервную копию и способ восстановления. Удаление столбцов, изменение типов и `NOT NULL` требуют проверки существующих данных. При необходимости разделите изменение на добавление совместимой схемы, заполнение данных и последующее ужесточение ограничений.

### 2. Добавить SQL-пару

Создайте вручную два файла с одинаковыми версией и описанием:

```text
backend/migrations/<YYYYMMDDHHMMSS>_<description>.tx.up.sql
backend/migrations/<YYYYMMDDHHMMSS>_<description>.tx.down.sql
```

Версия должна быть уникальной и больше всех существующих; ориентируйтесь на фактические имена файлов. Не переименовывайте и не редактируйте уже применённые миграции: исправление оформляется новой парой. CLI проекта не предоставляет команду генерации.

Пример добавления необязательного поля (имена заменить под задачу):

```sql
-- up
ALTER TABLE users ADD COLUMN display_name text;
```

```sql
-- down
ALTER TABLE users DROP COLUMN display_name;
```

`down` должен отменять структуру в обратном порядке зависимостей. Удаление поля уничтожит его значения: обратный SQL не заменяет резервную копию. Явно опишите невосстановимые изменения данных.

Суффикс `.tx` включает транзакцию Bun для отдельного файла; вся группа не является одной транзакцией. Не добавляйте собственные `BEGIN`/`COMMIT`. Операции вроде `CREATE INDEX CONCURRENTLY` нельзя помещать в такую транзакцию; для них отдельно спроектируйте нетранзакционную миграцию и восстановление после частичного выполнения. Учитывайте двухминутный таймаут CLI и блокировки PostgreSQL.

Регистрировать каждый SQL-файл в Go не нужно: его подхватит `Discover`. При использовании собранного мигратора пересоберите его — SQL встроен в бинарник. Согласуйте модели, запросы и API с новой схемой.

### 3. Подготовить локальную проверку

```sh
make setup
make infra-up
docker compose exec postgres createdb -U uptime uptime_migrations_test
```

Создание базы выполняется один раз; если она уже существует, сначала убедитесь, что это выделенная база для проверки. Создайте вне Git отдельный env-файл, например `/tmp/uptime-migrations.env`, с содержимым:

```dotenv
DATABASE_URL=postgres://uptime:uptime_local@127.0.0.1:55432/uptime_migrations_test?sslmode=disable
```

Для CLI достаточно настроек БД; JWT и SMTP не требуются. Указывайте этот файл явно:

```sh
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-status
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-up
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-status
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-up
```

Последний `up` должен сообщить об отсутствии новой группы. Без `BACKEND_ENV_FILE` Make-команды загружают `backend/.env`. Значения из файла могут переопределить переменные shell, поэтому одного `DATABASE_URL=... make migrate-up` недостаточно для надёжного выбора другой базы. Относительный путь env-файла разрешается от `backend/`. Прямой `go run ./cmd/migrate ...` из `backend/` env-файл сам не загружает.

Даже `status` инициализирует служебные таблицы и берёт блокировку мигратора. Не считайте эту команду строго читающей операцией.

### 4. Проверить обновление с данными и откат

Проверка на пустой базе не доказывает корректность обновления существующих данных. На отдельной базе сначала примените миграции предыдущей версии из соответствующего checkout, добавьте характерные данные, затем выполните `up` новой версии. Проверьте сохранность данных и результат заполнения новых полей, включая `NULL`, дубликаты и значения на границах новых ограничений.

Для проверки отката именно новой миграции сначала примените предыдущую схему отдельным запуском `up`, а затем новую миграцию следующим запуском. Тогда новая миграция образует отдельную последнюю группу. Проверьте состав группы перед откатом:

```sh
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-down
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-status
BACKEND_ENV_FILE=/tmp/uptime-migrations.env make migrate-up
```

Выполняйте этот сценарий только на выделенной тестовой базе. Проверьте фактическую схему после `down` и после повторного `up`. Если первоначальный `up` применил все миграции, `down` может удалить все прикладные таблицы.

### 5. Применить в целевом окружении

После успешной проверки запишите исходный статус и применяемые версии. Используйте env-файл целевого окружения, выполните `migrate-up`, затем `migrate-status` и проверки схемы/данных из следующего раздела. Запускайте новую версию API после успешной миграции; при несовместимых изменениях заранее обеспечьте остановку обращений старой версии к изменяемой схеме.

При ошибке остановите дальнейшие шаги. В текущей конфигурации Bun может отметить миграцию применённой до выполнения SQL, а при откате — снять отметку до выполнения SQL. Поэтому `applied=true` и повторный `up` сами по себе не доказывают успех после сбоя. Сравните реальную схему, данные и служебные записи `bun_migrations`, определите уже выполненные файлы группы. Не удаляйте записи или блокировку вслепую и не запускайте `down` автоматически. План восстановления должен учитывать фактическое состояние и резервную копию. При `migration unlock failed` проверьте отсутствие активного мигратора перед восстановлением блокировки; команды `unlock` у CLI проекта нет.

## T — Проверка: когда готово

- [ ] Для новой версии есть согласованная SQL-пара; последствия для данных и отката описаны.
- [ ] На пустой базе `up` успешен, все ожидаемые версии имеют `applied=true`, повторный `up` не создаёт новую группу.
- [ ] SQL-проверки подтверждают реальные типы, nullable/default, индексы и ограничения; проверены данные, а не только статус мигратора.
- [ ] Обновление предыдущей схемы с данными и цикл `down → up` проверены на отдельной базе.
- [ ] Выполнены соответствующие автоматические проверки и проверен затронутый пользовательский сценарий.

Пример просмотра схемы локальной тестовой базы (замените таблицу на затронутую):

```sh
docker compose exec postgres psql -U uptime -d uptime_migrations_test -c '\d+ users'
```

Добавьте к задаче конкретные `SELECT` для проверки заполнения данных и проверки нарушений новых ограничений. Проверка `/api/v1/health` подтверждает доступность API, но не корректность всей схемы.

Автоматические проверки для изменения миграций:

```sh
export TEST_DATABASE_URL='postgres://uptime:uptime_local@127.0.0.1:55432/uptime_migrations_test?sslmode=disable'
make test-integration
make check
make build
```

**Интеграционные тесты удаляют схему `public` указанной базы.** Имя должно оканчиваться на `_test`, URL должен отличаться от `DATABASE_URL`. Не запускайте их на базе приложения или одновременно с ручной проверкой той же базы. Тесты используют `TEST_DATABASE_URL` из окружения, а не `BACKEND_ENV_FILE`; без него PostgreSQL-тесты пропускаются.

При добавлении миграции обновите ожидаемое количество в `TestPostgresMigrations` (на момент создания гайда — `len(list) != 6`) и добавьте проверки специфичного поведения изменения. Существующий тест применяет всю схему одной группой и проверяет полный откат; он не заменяет проверку обновления предыдущей версии с данными.

Для интеграционных изменений запустите оба приложения через `make dev`, проверьте кнопку статуса API и затронутый сценарий. Если использовали `BACKEND_ENV_FILE` только с настройками БД, для запуска API потребуется полноценное окружение по `backend/.env.example`.

В отчёте агента укажите версии и файлы, целевую БД без секретов, выполненные команды и результаты, проверки данных, последствия отката и пропущенные проверки с причинами. Не объявляйте миграцию проверенной на PostgreSQL, если интеграционные тесты были пропущены.
