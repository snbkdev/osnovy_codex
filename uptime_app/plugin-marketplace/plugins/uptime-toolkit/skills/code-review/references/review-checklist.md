# Чек-лист ревью uptime_app

Пройди все разделы для выбранного diff. Проверяй также вызываемый код и последствия изменения общего компонента. Неприменимые разделы помечай с причиной. Признаки ниже помогают искать дефекты, но не заменяют подтверждение конкретной проблемы.

## 1. Поведение и API-контракт

- [ ] Изменение решает заявленную задачу; сохранены нужные сценарии и совместимость.
- [ ] Методы, пути, статусы, параметры, JSON, nullable/optional-поля, пагинация и ошибки согласованы между Go и TypeScript.
- [ ] Для изменённых API-роутов есть актуальные Swaggo-аннотации, сгенерированные Swagger JSON/YAML/Go, ReDoc HTML и список операций в router_test.go. При ревью проверяй их, не перезаписывая.
- [ ] Проверены пустые данные, границы, неверный ввод, повторные запросы, отмена и недоступность зависимостей.

**Хорошо:** ошибка имеет стабильный код, клиент отображает её; сервер проверяет входные данные; значения по умолчанию совпадают с UI.
**Плохо:** клиент ожидает объект вместо массива; 200 при фактической ошибке; поле исчезло без обновления потребителей; повторная операция создаёт дубликаты.

## 2. Архитектура и границы слоёв

Зафиксированная архитектура — модульный Go-бэкенд с отдельными сервисами и репозиториями и Next.js-фронтенд с общим клиентом API. В проекте нет требования вводить универсальную Clean Architecture или новую папку для каждого слоя.

| Слой / путь | Ответственность и границы |
| --- | --- |
| backend/cmd/api | Composition root: конфигурация, подключение БД, сборка сервисов/репозиториев/HTTP, запуск воркеров, таймауты и graceful shutdown |
| backend/internal/httpapi | Роутинг, middleware, разбор HTTP, DTO, перевод ошибок в ответы и Swaggo; сервисы передаются через интерфейсы; без SQL и бизнес-процессов |
| backend/internal/auth, monitor | Доменные сервисы, правила и валидация, типы и интерфейсы репозиториев; без зависимости от HTTP и Bun/storage |
| backend/internal/storage | Bun/PostgreSQL, модели хранения, реализация репозиториев, транзакционные границы и почтовый outbox/воркер; ORM-типы не выходят наружу |
| backend/internal/avatar, mail, identifier, config | Файловое хранилище аватаров, SMTP, идентификаторы, чтение и валидация конфигурации; без HTTP-роутинга |
| backend/cmd/migrate, migrations | Явные миграции схемы; API не применяет их при старте |
| frontend/src/app | App Router: страницы, layout, глобальные стили и композиция UI |
| frontend/src/components | Переиспользуемые React-компоненты; браузерное взаимодействие в client components |
| frontend/src/lib | Общий HTTP-клиент, типы и предметные API-функции; session.ts координирует access token в памяти, refresh и вкладки |
| frontend/src/pages/api/[...path].ts | Серверный потоковый прокси /api/* к Go API, доверенная передача IP с PROXY_SECRET; секреты остаются на сервере |
| frontend/public, next.config.ts | Статические ресурсы и конфигурация Next.js |

- [ ] Зависимости соблюдают эти границы; новый бизнес-сценарий не реализован напрямую в UI, HTTP-обработчике или SQL-клиенте фронтенда.
- [ ] Не раскрыты модели хранения/PasswordHash/внутренние поля через API.
- [ ] Переиспользование устраняет повторение логики, без лишних абстракций и несогласованных копий клиентов/типов.

**Хорошо:** обработчик преобразует ввод и вызывает сервис; storage реализует доменный интерфейс; UI обращается через src/lib.
**Плохо:** HTTP-обработчик строит SQL; auth импортирует storage; React знает про БД; новый компонент вручную повторяет refresh-логику session.ts.

## 3. Go: корректность и эксплуатация

- [ ] Ошибки обработаны на нужном уровне; errors.Is/As работают с обёртками; клиенту не возвращаются внутренние SQL/SMTP-ошибки.
- [ ] context и отмена передаются вниз; HTTP/SMTP/БД имеют подходящие таймауты; ресурсы закрываются.
- [ ] Горутины завершаются; общие map/state защищены; нет гонок, deadlock и неограниченных очередей.
- [ ] Корректны zero/nil, integer/duration-преобразования, время и единицы измерения; ограничения памяти и размеров входа явные.
- [ ] Запуск, worker failure и shutdown не теряют ошибки или незавершённые операции.

**Хорошо:** запрос БД принимает request context; обработчик переводит доменную ошибку в нужный статус; владение ресурсом понятно.
**Плохо:** проигнорированный err; panic на пользовательском вводе; context.Background в операции запроса без причины; горутина без способа остановки.

## 4. PostgreSQL, транзакции и миграции

- [ ] Запросы параметризованы; доступ ограничен user_id/владельцем, включая курсоры и вложенные выборки.
- [ ] Уникальность, лимиты, выдача/ротация токенов, outbox и связанные изменения атомарны при параллельных запросах.
- [ ] Порядок блокировок согласован; нет новых N+1, полного неограниченного чтения или пагинации без стабильного порядка.
- [ ] Миграции соответствуют docs/guides/migrations.md: новые пары up/down, совместимость с данными и предыдущей версией, индексы/constraints, последствия отката.
- [ ] Интеграционные тесты не могут удалить схему рабочей БД; пропущенные PostgreSQL-тесты явно отмечены.

**Хорошо:** квота проверяется в транзакции с подходящей блокировкой; SQL ограничивает владельца; миграция проверяет обновление существующих данных.
**Плохо:** check-then-insert вне транзакции; запрос по id без владельца; редактирование применённой миграции; утверждение об успешной миграции только по статусу Bun.

## 5. Next.js, React и пользовательские сценарии

Перед выводами о Next.js API прочитай подходящий раздел установленной документации frontend/node_modules/next/dist/docs/; версии в package.json важнее памяти о старых релизах.

- [ ] Корректны server/client boundaries, доступ к window/navigator, SSR и hydration; серверные модули не попадают в браузерный import graph.
- [ ] Effects имеют нужные зависимости/cleanup; асинхронные ответы не перезаписывают новое состояние; повторный рендер не создаёт запросы/подписки бесконечно.
- [ ] Session refresh остаётся согласованным между параллельными запросами/вкладками; logout не восстанавливает старую сессию.
- [ ] Запросы идут на относительные /api/* через общий клиент; приватные ответы не кешируются между пользователями.
- [ ] Есть loading/error/empty/success состояния, защита от нежелательной повторной отправки и сохранение понятной обратной связи.
- [ ] Сохранены label, фокус, клавиатура и семантика; интерактивные элементы доступны.
- [ ] strict TypeScript не обойдён необоснованным any, assertions или non-null; новые типы отражают реальные данные.

**Хорошо:** эффект отписывается; старый ответ игнорируется после смены пользователя; ошибка формы видима; секрет читается только в server proxy.
**Плохо:** токен в localStorage без рассмотрения существующей модели; секрет в NEXT_PUBLIC_*; общий кеш данных пользователя; кнопка без доступного имени.

## 6. Безопасность и секреты

- [ ] В diff и новых файлах нет действующих ключей, паролей, токенов, приватных ключей, env с секретами, дампов и PII; проверь также fixtures, snapshots, логи и собранные артефакты. Не открывай все локальные .env без необходимости.
- [ ] Идентичность и права проверяются сервером на каждой защищённой операции; объект принадлежит пользователю, запрет по умолчанию.
- [ ] JWT проверяет подпись, алгоритм, issuer/audience/expiry; refresh/reset/verification сохраняют срок, одноразовость/ротацию и существующие replay-защиты; пароли хешируются подходящим существующим механизмом.
- [ ] Cookie-флаги, SameSite/CSRF/Origin, CORS и rate limits соответствуют потоку аутентификации; UI-валидация не заменяет серверную.
- [ ] Прокси удаляет недоверенные forwarded-заголовки и формирует доверенный IP из сокета; PROXY_SECRET не берётся из браузера.
- [ ] SQL/command injection, XSS, опасный HTML/URL и редиректы предотвращаются на реальном sink; загружаемые файлы проверены по содержимому, размеру и безопасному пути.
- [ ] Если изменение действительно добавляет сетевое обращение к пользовательскому URL: SSRF, private/link-local/metadata IP, DNS/rebinding, redirects и лимиты ответа учтены. Само хранение URL ещё не доказывает наличие SSRF.
- [ ] Новые зависимости/lockfiles, scripts и конфигурация не добавляют неожиданные сетевые вызовы или раскрытие секретов; не делай выводов об уязвимости версии без подтверждения источником.

**Хорошо:** env.example содержит очевидные заглушки; SQL параметризован; права проверяются до чтения; логи не содержат credentials.
**Плохо:** рабочий API key в fixture; доверие X-Forwarded-For из браузера; доступ к чужому объекту по id; произвольный путь для upload.

Сканер секретов, если уже настроен, — дополнительная проверка. Отсутствие совпадений и зелёный lint не доказывают безопасность. Найденный секрет не копируй в отчёт.

## 7. Тесты и достоверность проверок

- [ ] Изменённое поведение имеет подходящие позитивные, негативные и граничные тесты; регрессионный тест воспроизводит дефект.
- [ ] Для auth/прав проверены отказ, чужой объект и просроченные/повторные данные; для конкурентности — реальное конкурентное поведение.
- [ ] Go: testing/httptest рядом с кодом, storage-интеграции для SQL-инвариантов; mocks не скрывают проверяемую ошибку.
- [ ] Frontend: Playwright auth-сценарии или подходящая воспроизводимая проверка UI; отсутствие unit-runner не является само по себе дефектом.
- [ ] Для соответствующего изменения выполнены build/интеграции/браузерные проверки по AGENTS.md либо перечислены ограничения. Нет выдуманного порога coverage; оцени покрытие рисков.
- [ ] Разделены результаты статического анализа, тестов и ручного анализа; пропуски и baseline failures не представлены как pass.

**Хорошо:** тест проверяет observable response и состояние; ошибка до исправления воспроизводится; PostgreSQL skip явно отражён.
**Плохо:** тест повторяет реализацию или проверяет только мок; удалены assertions; проверен только happy path критической операции; lint назван тестом безопасности.

## 8. Именование, мёртвый код и сопровождение

- [ ] Go: gofmt, имена пакетов lowercase и корректная экспортность; TypeScript: PascalCase компонентов, kebab-case файлов, @/ imports и соглашения App Router.
- [ ] Имена переменных/функций отражают предметный смысл, единицы и побочные эффекты. Короткие идиоматические Go-имена не считаются дефектом автоматически.
- [ ] Нет ненужных экспортов, недостижимых веток, устаревших helpers/flags/imports и закомментированных реализаций. Перед объявлением dead code проверь интерфейсы, reflection, регистрацию, build tags и внешних потребителей.
- [ ] Нет новых копий одной логики, скрытых magic values или подавления lint/typing без объяснения.
- [ ] Изменения env/dependencies отражены в env.example и lockfiles; генерация воспроизводима, генерируемые файлы не правились вручную.

**Хорошо:** intervalSeconds явно указывает единицы; один helper для общего поведения; удалённый роут удалён также из контракта.
**Плохо:** getData меняет сессию; два расходящихся API-клиента; blanket eslint-disable; неиспользуемый код сохранён «на всякий случай».
