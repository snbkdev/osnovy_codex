# Uptime App

Мониторинг доступности сервисов: Go API, Next.js и авторизация по email с JWT, PostgreSQL и Bun ORM. Вход доступен после подтверждения адреса. Поддерживаются выход, ротация refresh-токенов и восстановление пароля.

## Локальный запуск

Нужны Go 1.25+, Node.js 20.9+, npm и Docker Compose.

```sh
make setup
make infra-up
```

PostgreSQL доступен на `127.0.0.1:55432` (в контейнере — `5432`), чтобы не конфликтовать с локальным PostgreSQL. Mailpit: SMTP `127.0.0.1:1025`, интерфейс писем http://localhost:8025. Данные БД сохраняются в Docker volume. `make infra-down` останавливает инфраструктуру, сохраняя данные.

Заполните `backend/.env`, используя `backend/.env.example`. Для `JWT_SECRET` и `MAIL_ENCRYPTION_KEY` сгенерируйте **два независимых** значения:

```sh
openssl rand -base64 32
openssl rand -base64 32
```

Для `PROXY_SECRET` сгенерируйте ещё одно значение и запишите его одинаково в `backend/.env` и `frontend/.env.local`:

```sh
openssl rand -hex 32
```

Go читает окружение процесса; `.env` автоматически не загружается. В терминале API экспортируйте подготовленные настройки (env-файл должен содержать совместимый с shell синтаксис):

```sh
set -a
. ./backend/.env
set +a
make migrate-up
make dev
```

`make dev` запускает API и Next.js вместе, загружает `backend/.env` и останавливает оба процесса по `Ctrl+C` или при завершении одного из них. Для остановки из другого терминала выполните `make stop` из той же копии проекта. Повторный `make stop` безопасен; повторный `make dev` при активном запуске завершится с подсказкой сначала остановить приложения. Команда управляет приложениями, запущенными через `make dev`.

PostgreSQL и Mailpit запускаются отдельно через `make infra-up`; миграции применяются явно. После обновлений схемы перед запуском выполните `make migrate-up`. Команды `make dev`, `make backend-dev`, `make migrate-up`, `make migrate-status` и `make migrate-down` загружают один и тот же `backend/.env`. Для другого env-файла передайте `BACKEND_ENV_FILE=/absolute/path/backend.env` перед любой из этих команд.

Для раздельного запуска в двух терминалах:

```sh
make backend-dev
make frontend-dev
```

Next.js автоматически читает `frontend/.env.local`. Приложение: http://localhost:3000. API health: http://localhost:8080/api/v1/health. При активной сессии `/login` перенаправляет на главную после восстановления сессии. После входа дэшборд содержит шапку с профилем и отдельной кнопкой выхода; область содержимого пока пустая.

`make setup` создаёт только отсутствующие env-файлы, сохраняя существующие. Если файл уже был создан до добавления авторизации, перенесите новые настройки из примера вручную. Секреты и локальные env-файлы не коммитятся.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `HTTP_ADDR` | Адрес API, по умолчанию `:8080` |
| `AVATAR_DIR` | Папка локальных аватаров (по умолчанию `uploads/avatars` относительно backend); должна сохраняться между перезапусками |
| `DATABASE_URL` | Обязательная PostgreSQL DSN; локальный порт Compose — `55432` |
| `DB_MAX_OPEN`, `DB_MAX_IDLE` | Размер пула, по умолчанию 10 и 5 |
| `DB_CONN_LIFETIME` | Время жизни соединения, по умолчанию `30m` |
| `JWT_SECRET` | Base64 от минимум 32 случайных байт |
| `JWT_ISSUER`, `JWT_AUDIENCE` | Ожидаемые issuer и audience JWT |
| `MAIL_ENCRYPTION_KEY` | Base64 от отдельного ключа AES-256, ровно 32 байта |
| `PUBLIC_URL` | Origin фронтенда без пути, query и fragment; используется в письмах и Origin-защите |
| `APP_ENV` | `development` или `production` |
| `COOKIE_SECURE` | В production обязательно `true`, вместе с HTTPS `PUBLIC_URL` |
| `SMTP_ADDR`, `SMTP_USER`, `SMTP_PASSWORD` | Адрес SMTP и необязательные учётные данные |
| `SMTP_ALLOW_INSECURE` | Для локального Mailpit — `true`; в production запрещено |
| `MAIL_FROM` | Отправитель писем |
| `TRUSTED_PROXY_CIDR` | Сеть непосредственного Next.js-прокси; локально `127.0.0.1/32` |
| `PROXY_SECRET` | Общий секрет API и Next.js, минимум 32 символа при включённом доверии прокси |
| `API_URL` | Только на сервере Next.js: адрес Go API, по умолчанию `http://127.0.0.1:8080` |

Прокси `/api/*` берёт клиентский IP из серверного сокета, удаляет пользовательские IP-заголовки и передаёт адрес с `PROXY_SECRET`. API принимает этот адрес только от настроенной сети и при совпадении секрета. При дополнительном reverse proxy лимиты будут учитывать адрес его сокета; настройку такого развёртывания нужно согласовать отдельно. Секреты нельзя помещать в `NEXT_PUBLIC_*`.

Access JWT живёт 24 часа и хранится только в памяти браузера. Refresh-cookie — HttpOnly, SameSite=Strict, без Domain, с путём `/api/v1/auth`. Абсолютный срок сессии — 30 дней. Logout немедленно отзывает сессию, сброс пароля — все сессии. Обновления внутри вкладки объединяются, между вкладками сериализуются через Web Locks. Нужны современный браузер и безопасный контекст HTTPS либо localhost.

Токены писем находятся во фрагменте `#token=...`; страница удаляет его из адреса и выполняет POST после нажатия пользователем. Подтверждение действует 24 часа, сброс — 30 минут. Повторное письмо заменяет предыдущий токен. Очередь хранит зашифрованное содержимое, делает до пяти попыток с задержками 1, 2, 4 и 8 минут и удаляет содержимое после отправки или окончательной ошибки. SMTP-доставка допускает повтор письма при аварии между приёмом письма SMTP-сервером и фиксацией транзакции.

Первый выпуск рассчитан на **один API-процесс**: лимитер хранится в памяти. Production-секреты, параметры БД и SMTP передаются через окружение; TLS обязателен для фронтенда и SMTP. Смена JWT-ключа завершит доступ по старым JWT; смена ключа очереди без обработки ожидающих писем сделает их недоступными.

## Миграции и проверки

### CORS

Все маршруты API разрешают браузерные запросы только с точным `Origin`, заданным в `PUBLIC_URL` (схема, хост и порт). Чужой, `null`, пустой или повторный заголовок Origin отклоняется с 403 до вызова обработчика. Запросы без Origin продолжают работать для серверных клиентов; вход, refresh и logout по-прежнему требуют Origin. CORS не заменяет авторизацию.

Preflight `OPTIONS` разрешает методы GET, HEAD, POST и заголовки Accept, Accept-Language, Content-Language, Content-Type, Authorization, X-Uptime-Refresh-Request. Поддерживаются credentials и чтение Retry-After; служебные заголовки доверенного прокси не разрешены браузерным клиентам. Next.js-прокси передаёт Origin и CORS-заголовки. Браузерный клиент продолжает использовать относительные `/api/*`; политика SameSite=Strict для refresh-cookie сохраняется.

После изменения `PUBLIC_URL` перезапустите API. Для локального фронтенда используйте `http://localhost:3000`; `http://127.0.0.1:3000` — другой Origin. Пример проверки:

```sh
curl -i -X OPTIONS http://localhost:3000/api/v1/health \
  -H 'Origin: http://localhost:3000' \
  -H 'Access-Control-Request-Method: GET'
```

Ожидается 204 с `Access-Control-Allow-Origin: http://localhost:3000`; с `Origin: https://evil.test` ожидается 403 без разрешающего заголовка.

### Миграции

API проверяет подключение к БД и не изменяет схему автоматически. Перед запуском новой версии примените миграции:

```sh
make migrate-up
make migrate-status
```

`make migrate-down` откатывает последнюю группу миграций; откат группы с начальной схемой удаляет таблицы, а откат миграции профиля удаляет ФИО и дату рождения. Проверять откат следует только на тестовой базе. Команда использует блокировку Bun migrate.

```sh
make check
make build
```

`make check` запускает Go-тесты, go vet, ESLint и TypeScript. `make build` собирает `backend/bin/api` и Next.js. Запуск production-сборки: `./backend/bin/api` с окружением и `cd frontend && npm start` в другом терминале.

Интеграционные тесты требуют **отдельную БД** с именем, заканчивающимся на `_test`. Они удаляют её схему `public`, проверяют миграции, ограничения, откаты, одноразовые токены, ротацию, конкурентный сброс и повторную доставку. Не указывайте основную БД. URL тестовой БД должен отличаться от `DATABASE_URL`.

```sh
docker compose exec postgres createdb -U uptime uptime_auth_test
export TEST_DATABASE_URL='postgres://uptime:uptime_local@127.0.0.1:55432/uptime_auth_test?sslmode=disable'
make test-integration
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются; остальные тесты не требуют PostgreSQL.

Браузерная проверка требует запущенные API, Next.js и Mailpit. Используйте отдельную тестовую БД для API: сценарий создаёт пользователя, отправляет письма и меняет его пароль. Не запускайте одновременно несколько сценариев: они используют общий лимит IP. Playwright добавлен как devDependency; один раз установите Chromium:

```sh
cd frontend
npx playwright install chromium
cd ..
make test-auth-browser
```

Настройки сценария: `AUTH_TEST_URL` (по умолчанию `http://localhost:3000`), `MAILPIT_URL` (`http://localhost:8025`), `BROWSER_EXECUTABLE` (необязательный путь к установленному Chromium). Допускаются только локальные адреса. Проверяются письма, подтверждение, повторные ссылки, сессии и Web Locks в двух вкладках, однократный повтор API-запросов, сброс пароля, выход, доступные поля и состояния форм. Сроки токенов проверяются интеграционными тестами с управляемым временем; браузерный сценарий также проверяет отображение ответа об истёкшей ссылке.

## Ручной сценарий

Страница `/profile` доступна после входа через пункт «Редактировать профиль» в меню пользователя. ФИО (до 200 символов, обязательно хотя бы одна буква) и дата рождения сохраняются в PostgreSQL и восстанавливаются после перезагрузки. Дату рождения можно очистить; будущие и некорректные даты отклоняются. Email отображается только для чтения. Гости перенаправляются на `/login`.

Изменения профиля отправляются через защищённый `POST /api/v1/auth/profile` с `{full_name, date_of_birth}` (дата `YYYY-MM-DD` или `null`). Ответ содержит пользователя; `/me`, вход и refresh также возвращают новые поля. Перед запуском обновлённой версии примените `make migrate-up` с окружением backend.

1. Зарегистрируйтесь, проверьте запрет входа до подтверждения email.
2. Откройте письмо в Mailpit, подтвердите адрес кнопкой на странице и войдите.
3. Проверьте перезагрузку страницы, две вкладки, профиль в шапке и пустую область содержимого. Кнопка «Выйти» должна находиться справа от профиля и открывать страницу входа после выхода.
4. Запросите новое подтверждение/восстановление; предыдущая ссылка должна перестать работать.
5. Восстановите пароль через письмо. Старый пароль и старые сессии должны перестать работать; войдите с новым паролем.
6. Выйдите, проверьте завершение сессии в другой вкладке и после перезагрузки.
7. Проверьте отсутствующие, истёкшие и повторно использованные токены, ошибки сети, фокус клавиатуры и состояния загрузки.

## Структура

- `backend/cmd/api` — HTTP-сервер и жизненный цикл очереди.
- `backend/cmd/migrate`, `backend/migrations` — явные встроенные SQL-миграции.
- `backend/internal/auth` — сервис, интерфейс репозитория и криптография.
- `backend/internal/storage` — Bun-репозитории, транзакции и очередь писем.
- `backend/internal/mail` — SMTP-отправитель.
- `backend/internal/config`, `backend/internal/httpapi` — окружение и HTTP API.
- `frontend/src/app`, `frontend/src/components` — страницы и доступные формы.
- `frontend/src/lib` — клиент API и состояние сессии.
- `frontend/src/pages/api` — серверный прокси.
- `docs/auth-implementation-plan.md` — требования и чеклист реализации.

### Аватар профиля

В `/profile` выберите JPEG или PNG, настройте масштаб и положение в рамке, нажмите «Выбрать», затем «Сохранить аватар» или общую кнопку «Сохранить изменения». До сохранения доступен предпросмотр и отмена; после сохранения изображение обновляется в профиле и верхней панели.

`POST /api/v1/auth/avatar` принимает авторизованный Bearer-запрос с `multipart/form-data` и полем `avatar`, возвращает пользователя с `avatar_url`. Ограничения: 5 МБ, до 4096×4096 и 16 млн пикселей. Сервер проверяет содержимое и сохраняет квадратный PNG 256×256 без исходных метаданных. `GET /api/v1/avatars/{filename}` раздаёт файлы из `AVATAR_DIR` через обычный `/api`-прокси. URL аватаров публичные, имена случайные; повторная загрузка создаёт новый URL. Неиспользуемые файлы старше 24 часов удаляются фоновым обслуживанием при старте API и каждый час. Загрузка ограничена 10 попытками в час на пользователя; счётчик общий для API-инстансов в PostgreSQL. При нескольких API-инстансах `AVATAR_DIR` должен указывать на общий постоянный том.

Перед запуском обновлённого API примените миграции (`make migrate-up`). Папка `backend/uploads/` исключена из Git; при изменении `AVATAR_DIR` выбирайте каталог вне репозитория или добавьте его в исключения.

### Создание точек мониторинга

На главном экране авторизованного пользователя кнопка «Добавить сайт» открывает форму URL и частоты проверки. Введите полный HTTP/HTTPS URL и целое количество секунд, минут или часов. Интервал: от 5 секунд до 7 дней; например, 7 минут сохраняются как 420 секунд. URL не должен содержать логин и пароль; фрагмент `#...` удаляется, поскольку не участвует в HTTP-запросе.

`POST /api/v1/monitors` принимает Bearer-токен и JSON `{"url":"https://example.com","interval_seconds":420}`, возвращает созданную точку с кодом `201`. `GET /api/v1/monitors` возвращает до 20 точек текущего пользователя, от новых к старым. Для следующей страницы передайте `?before=<id последней точки>`; страница меньше 20 элементов означает конец списка. Дэшборд загружает страницы кнопкой «Загрузить ещё». Квота — 100 мониторов на пользователя, включая конкурентные создания; при превышении API возвращает `409 monitor_quota`. Чужой идентификатор пользователя передать нельзя. Список сохраняется в PostgreSQL и доступен после перезагрузки. На этом этапе сайты не опрашиваются; точки отображаются со статусом «Ожидает запуска мониторинга».

Перед запуском примените миграцию `20261015000004_monitors` через `make migrate-up`. Добавлены тесты сервиса, HTTP API и PostgreSQL, а также шаги создания точек в `frontend/scripts/auth-browser-check.mjs`.

### Ограничения ресурсов и доставка почты

Перед запуском этой версии выполните `make migrate-up`: миграция `20261015000005_resource_limits` добавляет общие счётчики запросов и статусы почты. Существующие завершённые письма получают `legacy_finished`, поскольку прежняя схема не различала успех и окончательный отказ.

В production API использует PostgreSQL для rate limit; отказ хранилища не отключает защиту. Вход ограничен отдельно по IP и email: 10 попыток за 15 минут. Сброс пароля — 10 попыток за 15 минут по IP. Почтовые операции сохраняют лимит 5 запросов в час отдельно по IP и email, refresh — 60 в минуту по IP. Ответ `429 rate_limited` содержит `Retry-After`. На процесс допускаются две одновременные операции регистрации/входа/сброса с Argon2; превышение возвращает `429 resource_busy`, без накопления очереди вычислений. Число API-процессов следует учитывать в общем бюджете памяти. Истёкшие счётчики удаляются каждый час.

В `mail_queue` поле `status` различает `pending`, `delivered`, `failed`, `legacy_finished`; `error_code` содержит `smtp_error` или `decrypt_error`. После пятого отказа письмо получает `failed`, чувствительный payload удаляется. Повторные попытки и окончательные отказы журналируются с ID очереди, номером попытки и безопасным кодом, без email, токенов и тела письма. Функция `storage.DeliveryStats()` предоставляет счётчики текущего процесса; постоянные показатели можно получать SQL-агрегацией по `status` и `attempts`. Например: `SELECT status, count(*) FROM mail_queue GROUP BY status;`.

### Повтор refresh после потери ответа

Перед запуском примените `20261015000006_refresh_retry` через `make migrate-up`. Клиент передаёт случайный 256-битный `X-Uptime-Refresh-Request` и один раз повторяет refresh при сетевой ошибке или ответе 503/504, удерживая Web Lock. Сервер восстанавливает тот же следующий refresh-токен только для той же пары старого токена и ключа запроса, в течение 30 секунд после первой ротации и пока следующий токен не использован. В БД сохраняются только хеши; следующий токен вычисляется HMAC с отдельным контекстом на основе серверного ключа. Повторы с другим ключом, после окна или после использования следующего токена отзывают сессию. Logout и сброс пароля имеют приоритет над восстановлением. Запросы без ключа сохраняют строгую прежнюю политику replay.

Ключ повтора живёт только в памяти текущего запроса: после перезагрузки страницы или двух неудачных попыток может потребоваться повторный вход. Перехват одновременно старого токена и ключа запроса допускает восстановление в пределах указанного окна; это ограниченный компромисс доступности, а не общее разрешение повторного использования токенов.

HTTP-обработчики используют общий строгий JSON-декодер и identity из middleware; изменения профиля и аватара дополнительно проверяют сессию в транзакции. Локальные файлы аватаров обслуживает `internal/avatar.LocalStore` через интерфейс `Store`. Генерация ID вынесена в `internal/identifier`. На frontend транспорт находится в `lib/http-client.ts`, состояние сессии — в `lib/session.ts`, операции профиля — в `lib/profile-api.ts`; `lib/auth.ts` сохраняет публичный интерфейс для компонентов.
